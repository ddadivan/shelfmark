# apps/web

Angular 22 client (CSR only, zoneless). Read `docs/PROJECT.md` 5.1 and 7 first. Load the `angular-v22-rules` skill before writing code — it is authoritative.

## Layout (`src/app/`)

- `app.ts`, `app.html` (only `<router-outlet />`), `app.config.ts`, `app.routes.ts`
- `core/` — app-wide singletons: `i18n/`, `theme/`, `api/`, later guards, interceptors, `AuthStore`
- `features/<name>/` (ADR 0042) — `<name>.page.ts|html|scss|spec.ts` (default export, lazy via `loadComponent`) at the root with `*.routes.ts`, guards and `provide-*-api.ts`; `components/<sub>/` sub-components (own `models/` and private helpers stay with them); `pages/<sub>/` further routed pages; `directives/`; `services/` (`*.service.ts`, `*.store.ts`); `utils/` pure helpers with their specs; `http/`, `mock/`, `models/`. A feature of one page and at most one component stays flat. `core/`, `shell/` and `stores/` keep their own layout
- `shell/` — layout around pages; `stores/` — NgRx SignalStore stores
- `src/testing/` — spec-only helpers (axe runner, translated component factory); excluded from the app build
- File names `kebab-case.<type>.ts`. Types live one per file in a `models/` folder next to their use (`<name>.type.ts`, `.interface.ts`, `.const.ts`); no TS `enum` (fixed value sets are `as const` objects, ADR 0024); no `any`, no `@ts-ignore`.

## Rules

- Translation keys `feature.section.key` in `core/i18n/en.json`. No UI text in templates or TS (brand name in `index.html` is the only exception).
- Languages (#274): `en.json` is the source; `fr.json`, `de.json`, `it.json`, `es.json`, `pt.json` (Brazilian) and `uk.json` (Ukrainian, #404) sit next to it; all seven, English too, are lazy chunks (#339). **A new or changed key goes into every language file in the same change** (natural, concise product tone; sentence case where the language uses it; keep `{{placeholders}}` and `{name}`); `core/i18n/translations.spec.ts` fails on a missing or extra key, a changed placeholder or missing plural categories. Plural keys: build them with `pluralKey(base, count)` (`Intl.PluralRules` of the active language) and give each language the categories it needs (`one`/`other`; French, Italian, Spanish and Portuguese also `many`; Ukrainian `one`/`few`/`many`/`other`). Language names are `LANGUAGE_NAMES` (each in its own name, not translated).
- Locale only through `LocaleService` (`core/i18n`), the only writer of `<html lang>` and of Transloco's active language: `init()` (app initializer: reads `localStorage` `sm-language`, resolves "Match my browser" from `navigator.languages`, loads the lazy file before the first render), `apply(settings)`, signals `settings`, `lang` (= `activeLang`, set once the file is loaded), `wantedLang`, `browserLang`, `locale` (BCP 47 for `Intl`), `firstDay` (no `spellcheck` since #326: the note field always spell-checks; a stored copy that still has the key is read without it); formatting `formatDate` (date format), `formatTime` / `dateTimeFormat` (clock), `formatWeekday`, `formatRelative`, `formatNumber`, pipe `appDate`. Never hard-code `'en'`/`'en-GB'` or call `getActiveLang()` for `Intl`, and never use Angular's `DatePipe`. The account wins: `UserSettingsStore` applies it when `languageSaved`, else saves a valid local choice once; `setLanguage(change)` is optimistic with rollback. `translate()` is not reactive: a `computed` that builds labels with it reads `activeLang()` (or `pluralKey`, which does), so it follows a switch.
- Layout for translations (Languages mockup): plan for 40% longer strings; buttons never cut their text (`ui-button wrap` where a label may wrap), toolbars and saved views wrap, sidebar rows and card titles truncate with "…", fixed-width controls fit the longest language; check French, German and Ukrainian on desktop and the 360px phone.
- Appearance only through `ThemeService` (`core/theme`), which owns `html[data-theme]` (`light` | `dark` | `custom`), `html[data-custom-base|accent|background|corners]`, `html[data-motion]`, the layout attributes of #285 (`LAYOUT_ATTRIBUTE`: `data-text-size`, `data-font`, `data-density`, `data-card-preview|site|notes|tags`, left out for the defaults; the colour bars of #418, `data-folder-highlight`, are gone with #440 and a stored layout that still has the key is read without it) and `color-scheme` (from the base), and calls `ReducedMotion.setAppReduced`. An own accent sets the four accent tokens and an own page background (#335) `data-custom-background="own"` and `--bg` on `html` (CSSOM, nearest readable shade). Never set them elsewhere (one exception, #410: `public/boot-skeleton.js` copies a stored `light` / `dark` to `html[data-theme]` for the first paint of the app skeleton; `init()` sets the same value). API: `init()` (idempotent, app initializer: reads `localStorage` `sm-theme`, `sm-custom-theme`, `sm-motion`, `sm-layout` for the first paint, follows the system scheme and other tabs through the `storage` event), `setPreference` / `setCustomTheme` / `setMotion` / `setLayout` / `apply(appearance)` (apply and remember locally), signals `preference`, `customTheme`, `motion`, `layout`, `resolved` (the base) and `appearance`. The account is the source of truth: `UserSettingsStore` applies `/api/me/settings` when it loads (only when `appearanceSaved`; otherwise a valid local appearance, `hasStoredAppearance()`, is kept and saved once, silently) and `setAppearance(change)` saves a change optimistically (rollback on failure); UI changes go through the store. Script-driven motion checks `ReducedMotion` from `@shelfmark/ui`, never `matchMedia` directly.
- Styles: tokens only, `rem` / `em` (breakpoints in `em`), both themes, phone from 360px, honour `prefers-reduced-motion`.
- Breakpoints (#316): navigation switches at 64em. `ViewportService.compact` (and the Sass `compact` mixin) is the mobile shell below it (Shelf block 1): a top bar with the logo (link to the library) at the start and the account avatar at the end (no search field: search is the tab bar's Search tab, `/` and the other entries stay; the avatar's menu, a bottom sheet, holds Settings; the top bar steps aside on pushed pages and on the settings pages), the tab bar Today, Library, Add, Search, Ask (Library is current only on `/library`; pressed on a feed or folder it opens the Library page and pressed again goes back there, round 11) (Tags in that place while Ask is off; no You tab: `/settings` is reached from the avatar), no sidebar, the Library / Tags pages, every `ui-menu` opened from a button as a bottom sheet, touch sizes, long press to select, swipe rows, the stacked bulk bar; `desktop` from 64em is the sidebar layout with the Shelf header search field (block 3, below); `ViewportService.wide` (and `wide`) from 80em is side by side and the preview split. `ViewportService.phone` (and `phone`) is only for small-screen details: bottom-sheet dialogs, the one Options menu, short labels, block buttons. Touch affordances (checkboxes, the star, "…") follow the input (`hover: none` / `pointer: coarse`), not the width. Content stays fluid (the card grid keeps `auto-fill` columns).
- Scrolling (#352): the app shell is exactly `100dvh` and never scrolls the document (`:root:has(app-shell)` is `overflow: hidden`; html and body have `overscroll-behavior: none`). Desktop: the sidebar, the main column (taller pages) and the library feed scroll; the mobile shell scrolls the main column (`ScrollRestorationDirective`: the position is stored per navigation id, Back / Forward put it back once the page has rendered, any other new URL, a new query included, starts at the top, a fragment change alone keeps it). Every inner scroll area has `overscroll-behavior: contain`. Landing, sign-in, privacy, changelog and about keep the document scroll. Never `position: fixed` on body. e2e: `support/scroll.ts` (`mainScrollTop`, `scrollMainTo`, `makePageTall`) instead of `window.scrollTo`; `scroll-restore.spec.ts` checks Back / Forward.
- Per-user data in `localStorage` (#363): a key that holds what one user did on this device (the folder emoji picker's "Recent", `sm-emoji-recent`; the folder pickers' recent move targets, `sm-recent-folders`, `RecentFoldersStore`; the latest due reminder the app-open note announced, `sm-reminders-seen`, #275; the closed extension banner of the library, `sm-extension-banner-dismissed`, #455; the export dialog's last export, `sm-last-export`, #387) is listed in `USER_STORAGE_KEYS` (`core/auth/models`); `SessionScope.end()` removes them on sign-out, expiry, a 401 and account deletion, whether or not their owner was created. Preferences of the device (theme, language, layout, the folded sidebar sections) are not listed.
- Foldable sidebar sections (#556): in the desktop sidebar the Pinned, Folders and Tags headings carry a chevron `ui-button` (`disclosure`, `aria-expanded`, `aria-controls` on the section body) that folds the section by height (`shell/sidebar/_sidebar-section.scss`: the tree's expand motion, none under reduced motion; the body stays rendered and turns `visibility: hidden` once folded). `SidebarSections` (`shell/sidebar/services`, root) keeps the folded ones in `localStorage` `sm-sidebar-collapsed` (a JSON list of `SIDEBAR_SECTION` values, read and written in try/catch, removed when all are open); the sidebar passes `collapsible` and `collapsed` to `app-sidebar-pinned` and `app-sidebar-tags`. Never on the phone (drawer, Library, Tags pages). "New folder" and "New tag" open a folded section first. e2e: `sidebar-sections.spec.ts`.
- Build UI from `libs/ui` components; no bare styled `<button>` / `<input>` in features.
- Components stay thin (#338): a page or component binds signals, calls services and renders. Logic lives elsewhere: state, derived lists, URL params and flows in a store or service (`services/*.service.ts`, `*.store.ts`; scoped to the page or dialog through its `providers` when it holds per-instance state), DOM behaviour (drag, keyboard, long press) in a directive (`directives/`), pure calculations in `utils/` with their own spec. Aim for at most ~250–300 lines of TS per page and ~200–250 per component; when one grows past that, extract before adding more. Specs move with the code they test; the component spec stays as the integration test.
- HTTP: relative `/api` URLs (`API_BASE_URL`); the dev server proxies `/api` to `http://localhost:3000` (`proxy.conf.json`).
- App skeleton (#410): `index.html` holds a static, `aria-hidden` skeleton of the shell (sidebar, top bar, feed cards; phone: cards and tab bar), styled by `src/_boot-skeleton.scss` (tokens, shimmer off under reduced motion) and shown only when `public/boot-skeleton.js` (external, CSP-safe) sets `html[data-boot-skeleton]`: `/demo`, or the `sm-session-hint` key (`session-hint.ts`: written by `AuthStore` on a session (`1`, or `demo` for a demo session, #440) and before an OAuth redirect, cleared for a guest and in `USER_STORAGE_KEYS`) outside sign-in, about, privacy and `/c/`. It is an overlay above `<app-root>`; `App.renderActivatedPage` removes it right after the first page is rendered ; the demo start page (`features/auth/demo-start.page`) renders the same markup as `BootSkeletonComponent` (`.boot--page`, `aria-busy`, a visually hidden polite status) instead of a logo and spinner, so skeleton to app is one continuous picture. The demo banner placeholder (`.boot__banner`, #440) is drawn on `/demo` and when the hint is `demo` (`html[data-boot-demo]`, set by the script) and always by `BootSkeletonComponent`; it copies the real `DemoBannerComponent` (48px on one line from 686px of width, 74px with the button under the text, 92px with the text on two lines below 476px, 12px taller on touch) and `boot-skeleton.spec.ts` compares banner, title and first card between skeleton and app. Shelf 14-system: blocks are `surface-hover` radius 8, the sidebar thin lines, the 640px search, plain card blocks, the mobile shell's top bar (`.boot__topbar`, below 64em: a logo block and the avatar), no Ask button. The library's extension banner (#490; a Shelf sage strip) has one fixed height (64px, two lines of copy at most) so its placeholder (`.boot__extension`) matches: the script sets `html[data-boot-extension]` on a library path in a desktop-wide Chromium window without the split view when the banner is not closed (it repeats the brand lists and the dismissed key; `config-checks/boot-skeleton-script.spec.ts` keeps them in step), and `BootSkeletonComponent` draws it when `ExtensionBannerService.bannerShown()`. Keep the geometry in step with the shell and the library grid. The landing at `/` (`landingGuestOnly`) waits for the session only with that hint (or a loaded session): a first visit renders the landing at once and asks the session in the background, moving to `/links` if one turns up while still on `/`, so a cold API never holds the first paint.

- Tags pick what the touch projects run (ADR 0043): `desktop` runs every e2e test, `tablet` only tests tagged `@mobile` or `@tablet`, `phone` only `@mobile` or `@phone`. Tag with the `E2E_TAG` constant (`apps/web-e2e/src/models/e2e-tag.const.ts`): `test('…', { tag: E2E_TAG.Phone }, …)` or on a `test.describe`. `@phone`: the path exists only below 64em or with touch (tab bar, sheets, long press, swipe, You tab), or it is a core journey whose UI differs in the mobile shell. `@mobile`: the tablet layout matters too. A test that sets its own viewport is not tagged (it would only repeat the desktop run), unless it needs the touch device and skips on desktop: then it gets `@phone` and runs once. A test that branches on `isCompact` / `isPhone` / `hasTouch` needs a tag, or its compact branch never runs. Remove an e2e test only when a unit or component spec covers the same behaviour, and name that spec in the PR.
