# 0048. AI job runner on Vercel: a Postgres job table, `waitUntil` after the response, a per-user tick and a daily sweep, Message Batches for backfill

- Status: Proposed
- Date: 2026-11-17
- Source: issue #389 (parent #388), `docs/ai/IMPLEMENTATION-AI-1.md` section 1, `docs/ai/FEATURES.md` principles 2, 4, 5 and 7, `docs/PROJECT.md` 5.6 and 5.8; amends [0019](0019-vercel-deployment-architecture.md) and [0031](0031-rate-limiting-and-request-interceptors.md) on `maxDuration`; refines [0047](0047-ai-provider-models-and-cost.md) on where `AiProvider` lives

## Context

- AI-1 (F0 foundation, F1 tag and folder suggestions, F2 summaries) runs one model call per link (ADR 0047: `claude-haiku-5-5`, structured output). Saving a link must never wait for it, and off, no quota or a provider error must leave the app as it is today.
- The Add link dialog shows suggestions as soon as the preview loads (`AiTags.dc.html` 1–2), so a job can start before the link exists and must be picked up by the save.
- Hosting is Vercel Hobby ([0013](0013-vercel-hobby-hosting.md)): one function `api/index.mjs` with `maxDuration: 10` ([0019](0019-vercel-deployment-architecture.md)) and `REQUEST_TIMEOUT_MS = 8000` ([0031](0031-rate-limiting-and-request-interceptors.md)); Vercel Cron runs at most **once a day** on Hobby; two daily crons already exist behind `CronSecretGuard` ([0034](0034-demo-session-and-cleanup-cron.md), [0036](0036-trash-soft-delete.md)).
- One job needs a page excerpt (SSRF-safe fetch, up to 4 s) and a model call (up to 15 s). That does not fit in 10 s next to the response.
- Processing existing links goes through the Message Batches API (ADR 0047 point 3): results come back in minutes to hours and must be polled.
- Local dev and tests run on PGlite without a Vercel runtime; the mock provider is the only provider there (ADR 0047 point 5).
- `apps/api/CLAUDE.md` makes `SafeFetcherService` the only allowed outbound HTTP path; the Anthropic SDK makes its own HTTPS calls (precedent: `monitoring.service.ts` posts to the fixed Sentry host with `fetch`).

## Decision

1. **Job table.** `ai_jobs` holds one row per link job: `user_id`, `link_id` (nullable, same-user composite FK to `links(id, user_id)`, cascade), `draft_id` (nullable, unique per user), `kind` (`link`; room for later kinds such as embeddings), `source` (`save | draft | backfill | rewrite`), `status` (`pending | running | done | failed | skipped`), `reason`, requested `parts`, `language`, `attempts`, `not_before`, `lease_until`, `batch_id`, and `result` (validated output, kept only while a draft is not attached to a link). The save transaction (`POST /api/links`, `POST /api/links/batch`) inserts the row only when AI is on for the user and at least one part (tags, folder, summary) is requested; otherwise nothing changes for the save.
2. **Start after the response.** `AiBackgroundService.defer(task)` wraps `waitUntil` from `@vercel/functions`. Outside Vercel it is a no-op and the promise runs in the Node process, so `nx serve api` needs nothing else; tests swap in a deferrer they can await. A task claims its job with `UPDATE … SET status = 'running', attempts = attempts + 1, lease_until = now() + 60 s` on a row picked with `FOR UPDATE SKIP LOCKED`, reserves one link of quota, fetches the excerpt through `SafeFetcherService`, calls the provider, validates and writes the result. With time left it drains up to three more stale jobs of the same user.
3. **`maxDuration` 30 s.** `vercel.json` raises the function's `maxDuration` from 10 to 30 s (inside Hobby limits). `REQUEST_TIMEOUT_MS` stays 8000, so every HTTP request keeps its 504 at 8 s; only deferred work uses the extra time. This amends the 10 s figure in [0019](0019-vercel-deployment-architecture.md) and [0031](0031-rate-limiting-and-request-interceptors.md).
4. **Drafts.** `POST /api/ai/drafts` (from Add link, keyed by a per-dialog `draftId`) creates a `draft` job before the link exists. `POST /api/links` with `aiDraftId` attaches it inside the create transaction: if the job is done, its `result` is applied there and cleared; otherwise `link_id` is set and the runner applies the result when it finishes. Both paths lock in the order `folders:<userId>` → the job row (`FOR UPDATE`) → `tags:<userId>`, consistent with [0033](0033-links-search-cursor-idempotency.md). Unattached drafts are deleted after 24 hours.
5. **Catch-up without frequent crons.** `POST /api/ai/tick` (session, per user, rate limited) runs the user's stale jobs (pending for more than 30 s or with an expired lease), polls their open batches and advances their backfill, within a 6 s budget; the web app calls it every 15 s while the user has pending jobs or a running backfill. `GET /api/cron/ai-sweep` (daily Vercel Cron, `@AllowAnonymous()` plus `CronSecretGuard` at method level, listed in `PUBLIC_ROUTES`, the same GET exception as [0034](0034-demo-session-and-cleanup-cron.md)) does the same for all users within 25 s, fails jobs past three attempts and deletes old drafts.
6. **Retries.** Provider 429, 5xx, timeout or network error returns the job to `pending` with `not_before` after 30 s, 2 min and 10 min; after three attempts it is `failed` with reason `unavailable`. A refusal or output that fails validation is `failed` at once and nothing is shown (ADR 0047). A failed page fetch is not a failure: the job runs on URL and title. Quota is counted when the model is called and refunded when the provider failed without a response.
7. **Backfill through Message Batches.** Starting a backfill stores its state on the user's AI settings (keyset cursor over live links created before AI was enabled and without AI results). Each tick or sweep prepares the next chunk of up to 40 links (excerpts fetched with concurrency 8 inside the budget, never stored), creates one `backfill` job per link and submits one batch (`custom_id` = job id), recorded in `ai_batches`. Polls use `batches.retrieve`; an ended batch is read with `batches.results`, and every item goes through the same apply step as live jobs. Stop cancels open batches and keeps what is done. Backfill uses a one-time allowance separate from the monthly quota (author's decision: 5,000 links for the AI pack). Backfill and rewrite jobs **never auto-apply** a folder or tags.
8. **Mock provider.** The mock answers link jobs deterministically and answers a batch submission as already completed with its results, so it holds no state and works across Vercel instances (demo users on production).
9. **`AiProvider` stays server-side.** The `AiProvider` interface and the provider's input and output shapes (`{ tags, newTag, folder, summary, kind }`) live in `apps/api/src/ai/models/`; `libs/shared/contracts/src/ai/` holds only the request and response DTOs shared with the web app. This refines ADR 0047 point 1, which placed the interface in the contracts: the web app must never depend on provider shapes.
10. **Outbound exception for fixed provider hosts.** The official provider SDK may make HTTPS calls to its own fixed host (`api.anthropic.com`), never to a URL derived from user input. Only `apps/api/src/ai/providers/anthropic-ai.provider.ts` may import `@anthropic-ai/sdk`, enforced by an ESLint `no-restricted-imports` rule in `apps/api/eslint.config.mjs`. Every page fetch for AI still goes through `SafeFetcherService`. `apps/api/CLAUDE.md` documents the exception next to the Sentry tunnel precedent.

## Consequences

- Saving never waits for the model; a suggestion arrives within seconds in the normal case and, if an invocation was cut short, at the next tick or within a day.
- With Shelfmark closed, a backfill continues only through the daily sweep, so the copy says it is faster while Shelfmark is open and finishes within a day otherwise (author's decision); no GitHub Actions schedule for now.
- Two new dependencies, `@anthropic-ai/sdk` and `@vercel/functions`, pinned (ADR 0001) and imported statically in `api/index.mjs` for Vercel's file tracer (`vercel-entry.spec.ts`).
- A third Vercel cron. If Hobby refuses the extra cron, the AI sweep runs from the trash-cleanup handler instead.
- Deferred work can use up to 30 s per invocation, which counts against the Hobby compute allowance; at two users this is negligible.
- A job killed at `maxDuration` stays `running` until its lease expires, then the tick or sweep retries it.
- Revisit when Shelfmark leaves Hobby (frequent crons or a queue product make the tick unnecessary) or when job volume makes per-user ticks too coarse.

## Alternatives considered

- **Vercel Cron draining the table** — natural, but Hobby crons run once a day, so suggestions would arrive up to a day late; kept only as the safety-net sweep.
- **Vercel Queues or Workflow** — durable retries and fan-out, but a new product with plan-dependent limits, a second runtime model and no local equivalent on PGlite.
- **Synchronous model call inside the save** — simplest, but breaks "saving never waits" and the 8 s request timeout.
- **External scheduler (GitHub Actions every 15 minutes calling the sweep)** — would let a backfill finish with Shelfmark closed, but puts `CRON_SECRET` in GitHub and has best-effort timing; declined by the author for now.
- **`AiProvider` in `libs/shared/contracts`** (ADR 0047 as written) — exposes server-only shapes to the web bundle's dependency graph for no benefit.
