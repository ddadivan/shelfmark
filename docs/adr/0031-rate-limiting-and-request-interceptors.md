# 0031. Rate limiting, request logging, timeout and CSRF origin check

- Status: Proposed
- Date: 2026-11-07
- Source: issue #123; `docs/PROJECT.md` 5.2, 5.8 ("API abuse"), 6; builds on [0007](0007-api-security-baseline.md), [0029](0029-global-session-guard-and-isolation-harness.md), [0030](0030-better-auth-integration.md)

## Context

ADR 0007 deferred throttling and the Logging and Timeout interceptors to a follow-up that lands before the links API (#72). Issue #123 also carries the CSRF origin check proposed in the #65 security review. The API runs as one Vercel Function with many instances, behind Vercel's proxy.

## Decision

1. **Throttler.** `@nestjs/throttler` 6.7.1 (exact pin, no install scripts, so no `allowScripts` entry), registered as the first `APP_GUARD` in `AppModule`, before the CSRF guard and the session guard: a flood is rejected before any database lookup. One `default` throttler (120 requests per minute per client IP overall: a custom `generateKey` drops the route from the bucket key, whereas the v6 default would give every route its own bucket). `@RateLimit` overrides keep a per-route bucket. Stricter limits are named in `RATE_LIMIT` (`Auth`, `AddLink`, `Preview`, `Demo`, `Export`) and applied per route with `@RateLimit(RATE_LIMIT.X)`; #72, #67 and #107 only decorate their handlers. `GET /api/health` opts out with `@SkipThrottle()`.
2. **Auth routes.** Better Auth is mounted outside Nest's router, so the guard never sees `/api/auth/*`. `createAuthRateLimitMiddleware` (after the allow-list, sharing the throttler storage) applies `RATE_LIMIT.Auth` (20 per minute per IP) to sign-in, callback and sign-out. `get-session` is exempt (called on every page load). Better Auth's own limiter stays as a second layer.
3. **Client IP.** `x-vercel-forwarded-for` (set by Vercel, not client-controllable), then the first hop of `x-forwarded-for`, then the socket address; invalid values are skipped and IPv6 is grouped by its /64. IPv4-mapped IPv6 (`::ffff:a.b.c.d`) is unwrapped to IPv4 first, otherwise all IPv4 clients would share one /64 bucket. The forwarded headers are honoured only when `VERCEL=1` or with the explicit opt-in `TRUST_PROXY_HEADERS=1` (never implied by a non-production `NODE_ENV`; `vitest.setup.ts` sets it for specs), so a deployment without a trusted proxy cannot be bypassed with a forged header. Per-user limits are not part of this change: the limiter runs before the session is known, and every limit specified by the issue is per IP.
4. **429.** The throttler sets `Retry-After` (seconds); `AllExceptionsFilter` renders the `ApiError` shape (the auth middleware writes the same shape itself).
5. **Storage: in-memory, best-effort.** Counters live in the memory of one function instance. Under load Vercel runs several instances, and a cold start resets the counters, so the effective limit is higher than configured and is not shared between instances. This is acceptable for stage 1 (a portfolio project, no paid abuse surface) and is a known limitation. **Author decision pending:** a shared store, either a Postgres table (no new service, one extra query per request on a cold path) or Redis through the Vercel Marketplace (a new service and secret). The `ThrottlerStorage` interface makes the switch local to `createRateLimitOptions`. **The demo limit (5 per hour, #67) needs a shared store before it is enforceable:** with per-instance memory an attacker spread over instances, or a cold start, gets more than 5 demo sessions, so #67 must not rely on it as a hard quota until this decision is made.
6. **LoggingInterceptor.** One line per handled request: method, route pattern (never the query string), status, duration, request id. No bodies, headers, cookies, IPs or user data. Guards run before interceptors, so requests rejected by a guard (401, 403, 429) are not logged by it.
7. **TimeoutInterceptor.** `REQUEST_TIMEOUT_MS = 8000`, below the Vercel `maxDuration` of 10 s. A slow handler fails with `GatewayTimeoutException` (504, generic `ApiError` message, as for every 5xx). It stops waiting; it does not cancel the work, so a handler that timed out may still finish its writes. Write routes (#72) must therefore be idempotent or safe to retry (for example the duplicate-URL check) because the client sees a 504 for work that may have succeeded.
8. **CSRF origin guard** (`CsrfGuard`, global, after the throttler, before the session guard). For POST, PUT, PATCH and DELETE on Nest routes: a present `Origin` that is not one of the trusted origins (`BETTER_AUTH_URL` plus `BETTER_AUTH_TRUSTED_ORIGINS`) is a 403; a request with a body and a `Content-Type` other than `application/json` is a 415. `Sec-Fetch-Site: cross-site` is a 403 even with a trusted `Origin`; without an `Origin`, only `same-origin`, `none` or no `Sec-Fetch-Site` header is accepted (`same-site` is not), so non-browser clients still pass. `/api/auth/*` keeps Better Auth's own checks. No state-changing `GET` stays the rule.

## Consequences

- A guard-level 429 is never logged by `LoggingInterceptor`; add a middleware logger if abuse monitoring needs it.
- The CJS package is loaded by the ESM bundle as an external; `api/index.mjs` imports `@nestjs/throttler` and `rxjs` statically for the file tracer. Needs a Vercel preview check.
- Specs that sign in many times raise the auth limit through `createAuthTestApp({ authRateLimit })` (default effectively unlimited).
